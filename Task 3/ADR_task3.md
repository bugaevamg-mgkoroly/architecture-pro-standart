### <a name="_qmphm5d6rvi3"></a>**Решение**

**Основные компоненты и интеграции (по диаграммам):**

Диаграмма контекста [C4 Level 1](https://github.com/bugaevamg-mgkoroly/architecture-pro-standart/blob/architecture/diagrams/%D0%94%D0%B8%D0%B0%D0%B3%D1%80%D0%B0%D0%BC%D0%BC%D0%B0%20%D0%BA%D0%BE%D0%BD%D1%82%D0%B5%D0%BA%D1%81%D1%82%D0%B0%20%C2%AB%D0%9E%D1%82%D0%BA%D1%80%D1%8B%D1%82%D0%B8%D0%B5%20%D0%B4%D0%B5%D0%BF%D0%BE%D0%B7%D0%B8%D1%82%D0%BE%D0%B2%20%D0%BE%D0%BD%D0%BB%D0%B0%D0%B9%D0%BD%C2%BB%20MVP.png)

Диаграмма контейнеров [C4 Level 2](https://github.com/bugaevamg-mgkoroly/architecture-pro-standart/blob/architecture/diagrams/%D0%94%D0%B8%D0%B0%D0%B3%D1%80%D0%B0%D0%BC%D0%BC%D0%B0%20%D0%BA%D0%BE%D0%BC%D0%BF%D0%BE%D0%BD%D0%B5%D0%BD%D1%82%D0%BE%D0%B2%20%C2%AB%D0%9E%D1%82%D0%BA%D1%80%D1%8B%D1%82%D0%B8%D0%B5%20%D0%B4%D0%B5%D0%BF%D0%BE%D0%B7%D0%B8%D1%82%D0%BE%D0%B2%20%D0%BE%D0%BD%D0%BB%D0%B0%D0%B9%D0%BD%C2%BB%20MVP.png)

**Клиентские точки входа:**

Сайт банка (PHP + React.js) — для новых клиентов; отображает список депозитов, принимает заявки.

Интернет‑банк (ASP.NET MVC 4.5, MS SQL) — для действующих клиентов; отображает персонализированные ставки, принимает заявки с СМС‑подтверждением.

**Промежуточные сервисы:**

API‑шлюз — маршрутизация запросов, аутентификация, логирование, ограничение нагрузки.

Сервис расчёта ставок — получает данные из XLS/АБС, возвращает актуальные ставки для сайта и интернет‑банка.

Очередь сообщений (RabbitMQ) — буферизация заявок для надёжной доставки в АБС даже при временных сбоях.

**Ядро системы:**

АБС (Oracle, PL/SQL) — хранение данных счетов, проведение операций, подтверждение ставок, фиксация открытия депозитов.

Система кол‑центра (React.js + Java Spring Boot + PostgreSQL) — обработка заявок с сайта, коммуникация с клиентом, обновление статусов.

**Вспомогательные системы:**

СМС‑шлюз — отправка уведомлений о статусе заявки и открытии депозита.

Резервный ЦОД — автоматическое переключение при сбое основного ЦОД.

**Интеграции:**

Сайт/интернет‑банк → API‑шлюз → Сервис расчёта ставок → АБС.

Сайт → Система кол‑центра → Оператор → АБС.

АБС → Очередь сообщений → СМС‑шлюз.

Интернет‑банк ←→ АБС (через API‑шлюз, без прямого доступа).

Сервис расчёта ставок ←→ XLS‑файлы (периодическая синхронизация).

**Логика принятия решений:**

Использование API‑шлюза обеспечивает безопасность, мониторинг и ограничение нагрузки на АБС.

Сервис расчёта ставок изолирует АБС от частых запросов на получение ставок, снижает нагрузку.

Очередь сообщений (RabbitMQ) гарантирует доставку заявок даже при временных сбоях АБС, повышает надёжность.

Разделение клиентских точек входа (сайт для новых, интернет‑банк для действующих) соответствует бизнес‑процессу.

Приоритет существующих технологий (MS SQL, Oracle, ASP.NET) снижает затраты на поддержку и обучение.

Резервный ЦОД обеспечивает требуемый uptime 99,9%.

Шифрование трафика (TLS 1.3+) соответствует требованиям ЦБ РФ по защите данных.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

**1. Прямая интеграция интернет‑банка с АБС:**

**Плюс:** Упрощение архитектуры, уменьшение числа промежуточных компонентов.

**Минус:** Риск перегрузки БД АБС, нарушение требования о запрете прямого доступа; снижение надёжности.

**2. Использование Kafka вместо RabbitMQ:**

**Плюс:** Горизонтальное масштабирование, устойчивость к высоким нагрузкам, поддержка стриминга.

**Минус:** Несовместимость с текущей версией интернет‑банка (требуется миграция); дополнительные затраты на внедрение.

**3. Хранение ставок в отдельной БД (не в XLS):**

**Плюс:** Быстрый доступ, автоматизация обновлений, снижение зависимости от ручного ввода.

**Минус:** Дополнительные затраты на разработку, синхронизацию с АБС и миграцию данных.

**4. Отказ от СМС‑подтверждения в MVP:**

**Плюс:** Снижение нагрузки на СМС‑шлюз, упрощение процесса.

**Минус:** Нарушение требований безопасности (подтверждение операций обязательно); снижение доверия клиентов.

**5. Монолитная архитектура вместо микросервисов:**

**Плюс:** Простота развёртывания, меньше компонентов для мониторинга.

**Минус:** Сложность масштабирования, высокая связанность компонентов, риск сбоев при доработках.

**Недостатки, ограничения, риски**

**Недостатки выбранного решения:**

* Дополнительная задержка из‑за очереди сообщений (RabbitMQ).

* Необходимость поддержки промежуточного сервиса расчёта ставок (временное решение до миграции в АБС).

* Ограниченная масштабируемость АБС (вертикальное масштабирование только за счёт апгрейда железа).

* Зависимость от XLS‑файлов для ставок (риск ошибок ручного ввода, низкая автоматизация).

**Ограничения:**

* Запрет на изменение архитектуры АБС (нельзя добавлять новые API или менять схему БД).

* Несовместимость интернет‑банка с Kafka (в MVP).

* Ограниченные возможности горизонтального масштабирования АБС.

* Требования ЦБ РФ по хранению и передаче персональных данных (дополнительные затраты на шифрование и аудит).

**Риски:**

* Перегрузка АБС при резком росте заявок (требуется мониторинг и лимитирование запросов).

* Сбои в СМС‑шлюзе → задержка уведомлений → недовольство клиентов.

* Нарушение требований ЦБ РФ при недостаточной защите данных → штрафы и репутационные потери.

* Ошибки синхронизации между сайтом/интернет‑банком и АБС → расхождения в статусах заявок.

* Задержки в кол‑центре из‑за ручного ввода данных → снижение удовлетворённости клиентов.

* Сбои в резервном ЦОД → нарушение uptime 99,9% → финансовые потери.

* Нехватка экспертизы ПО
