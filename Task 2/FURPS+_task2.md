# Задание 2. Требований для цифровой трансформации банка «Стандарт»

| Код | Требования                         | Комментарий        |
|-----|------------------------------------|--------------------|
| **F** | **Функциональные (Functionality)**   |                    | 
| F1  | На сайте клиент должен видеть списк доступных депозитов с актуальными ставками | Ставки должны синхронизироваться с внутренним источником данных (пока — XLS, в перспективе — АБС) |
| F2  | Форма подачи заявки от клиента на депозит должна содержать ФИО и телефон | Данные передаются в систему кол‑центра для дальнейшей обработки |
| F3  | В интернет‑банке клиент должен видеть список персонализированных ставок по депозитам | Требуется интеграция с системой расчёта ставок (в перспективе — в АБС) |
| F4  | В интернет‑банке форма подачи заявки на открытие депозита должна включать счёт и сумму | После ввода данных — подтверждение через СМС‑код |
| F5  | СМС‑подтверждение операций (открытие депозита, изменение ставки) | Используем существующий СМС‑шлюз; требуется доработка механизма генерации кодов |
| F6  | В интернет‑банке клиент должен видеть список предодобренных кредитных предложений | Интеграция с системой скоринга и Кредитным конвейером |

| F8  | В интернет‑банке форма подачи заявки на кредит должна содержать указание счёта зачисления | Требуется подтверждение через СМС‑код |
| F9  | Информирование клиента по СМС об изменении статуса заявки (депозит/кредит) | Интеграция с СМС‑шлюзом; статусы берутся из АБС/Кредитного конвейера |
| F10 | В кол‑центре должна быть возможность просмотра и обработка заявок с сайта/интернет‑банка | Данные должны отображаться в существующей системе кол‑центра |

| U1  | Интерфейс сайта и интернет‑банка должен быть интуитивно понятный, с минимальными шагами для подачи заявки | Ориентир на аудиторию старшего возраста: крупные кнопки, чёткие подсказки |
| U2  | Должна быть организована единая дизайн‑система (цвета, шрифты, элементы) во всех каналах | Соблюдение корпоративного стиля банка |
| U3  | Мгновенный отклик интерфейса при подаче заявки (не более 500 мс) | Оптимизация загрузки справочных данных (сейчас >1 сек) |
| U4  | Адаптивность интерфейса под мобильные устройства | Клиенты часто используют смартфоны для доступа к банку |
| **R** | **Надёжность (Reliability)**          |              |
| R1  | Доступность сервисов 24/7 с уровнем uptime 99,9% | Требуется резервирование в ЦОД и автоматическое переключение |
| R2  | Защита персональных данных при передаче (сайт/интернет‑банк → системы банка) | Обязательное шифрование трафика (TLS 1.3+) |
| R3  | Резервное копирование данных депозитных/кредитных заявок | Ежедневное резервное копирование в зашифрованном виде |
| R4  | Обработка ошибок без потери данных | При сбое — сохранение заявки в очереди для повторной отправки |
| R5  | Защита от DDoS‑атак для публичных сервисов (сайт, интернет‑банк) | 	Использование CDN и файрволов |
| P   | Производительность (Performance)   |              |

| **S**   | **Поддерживаемость (Supportability)**  |              |
| S1  | Документирование API и интеграционных потоков | Для дальнейшего расширения системы |

| Код | Требования                         | Комментарий        |
|-----|------------------------------------|--------------------|
| **Группа 1. Интеграционная архитектура и взаимодействие компонентов** | 
| **АЗТ‑1 (F1, F3, P1, +R1)** | синхронизация ставок депозитов с внутренним источником данных с временем отклика API ≤ 300 мс. Запрет прямой интеграции интернет‑банка с АБС. | промежуточный сервис‑оракул (Broker Service) между интернет‑банком и АБС; кэширование ставок в Redis с TTL = 5 мин; API‑шлюз для маршрутизации запросов. |
| **АЗТ‑2 (F2, F4, F10, R4)** | гарантированная доставка заявок на депозит с обработкой ошибок без потери данных. | асинхронный workflow с использованием очереди сообщений (RabbitMQ) и механизмом повторных попыток. |
| **Группа 2. Безопасность и соответствие регуляторам** |
| **АЗТ‑3 (R2, R5, +R5, +R6)** | защита персональных данных на всех этапах передачи и хранения, защита от DDoS, поддержка резервного ЦОД. | TLS 1.3+ для всех публичных API; шифрование данных AES‑256 на уровне БД; CDN и файрволы для защиты от DDoS; автоматическое переключение на резервный ЦОД (≤ 2 мин).|

| **Группа 3. Производительность и масштабируемость** |
| **АЗТ‑5 (P2, P3, S3)** | обработка заявки ≤ 10 сек, поддержка 1 000+ пользователей, модульность кода. | горизонтальное масштабирование через Kubernetes (3 реплики); модульный дизайн с чётким разделением ответственности; асинхронная обработка тяжёлых операций.|

## Обоснование дополнительных требований

**1. Ограничение нагрузки на систему скоринга (+R4)**

**Почему:** Система скоринга критически важна для банка и испытывает пиковые нагрузки. Массовые предрасчёты могут привести к отказу сервиса.

**Решение:** Скоринг запускается только при явном запросе клиента (подача заявки).

**2. Запрет прямой интеграции с АБС (+R1)**

**Почему:** БД АБС уже перегружена. Прямой доступ из интернет‑банка увеличит нагрузку и риск сбоев.

**Решение:** Внедрение промежуточного сервиса-агрегатора данных.

**3. Горизонтальное масштабирование интернет‑банка (P3)**

**Почему:** Текущая инфраструктура (1 группа серверов) не выдерживает рост пользователей.

**Решение:** Развёртывание контейнеров в Kubernetes с автомасштабированием.

**4. Мониторинг и логирование (S4)**

**Почему:** Без отслеживания производительности невозможно выявлять узкие места.

**Решение:** Внедрение Prometheus + Grafana для визуализации метрик.

**5. Соблюдение требований ЦБ РФ (+R5)**

**Почему:** Банк обязан защищать персональные данные согласно ФЗ-152 и нормативам ЦБ.

**Решение:** Шифрование на уровне БД (TDE для Oracle/MS SQL), контроль доступа через RBAC.
