## Архитектурно‑значимые требования (АЗТ) для депозитного контура
1. Интеграционная архитектура
АЗТ‑1 (F4 + R1 + +R1)

Требование: Запрет прямой интеграции интернет‑банка с API АБС (+R1).

Решение: Внедрение промежуточного сервиса‑оракула (Broker Service) между интернет‑банком и АБС.

Обоснование:

Предотвращение перегрузки БД АБС (F4).

Обеспечение uptime 99,9% (R1) за счёт буферизации запросов.

Трассировка:

Код: BrokerService.DepositRequestHandler

Документация: «Раздел 3.2. Интеграционные потоки».

АЗТ‑2 (F1 + F3 + P1)

Требование: Время отклика API для ставок — ≤ 300 мс (P1).

Решение: Кэширование ставок в Redis с TTL = 5 мин.

Обоснование:

Синхронизация ставок с внутренним источником (F1).

Персонализация ставок в интернет‑банке (F3).

Трассировка:

Код: RateCacheService.GetCurrentRates()

Документация: «Раздел 4.1. Кэширование данных».

2. Безопасность и соответствие регуляторам
АЗТ‑3 (R2 + +R5 + +R6)

Требование: Шифрование данных на всех этапах (R2, +R5).

Решение:

TLS 1.3+ для API.

AES‑256 для хранения персональных данных.

Обязательная проверка сертификатов в ЦОД (резервный — +R6).

Обоснование: Соответствие требованиям ЦБ РФ (+R5).

Трассировка:

Код: SecurityMiddleware.EncryptPayload()

Документация: «Раздел 5.1. Криптографическая защита».

АЗТ‑4 (F5 + R4 + S4)

Требование: СМС‑подтверждение операций с гарантией доставки (F5).

Решение: Очередь сообщений (RabbitMQ) с повторной отправкой при ошибке.

Обоснование:

Обработка ошибок без потери данных (R4).

Мониторинг через Prometheus (S4).

Трассировка:

Код: SmsQueueProcessor.RetryFailedMessages()

Документация: «Раздел 6.3. Обработка уведомлений».

3. Производительность и масштабируемость
АЗТ‑5 (P3 + S3 + +R8)

Требование: Поддержка 1 000+ пользователей (P3).

Решение: Горизонтальное масштабирование через Kubernetes (развёртывание 3 реплик).

Обоснование:

Модульность кода (S3) для лёгкого добавления инстансов.

Ограничение на Kafka (+R8) → временное использование RabbitMQ.

Трассировка:

Код: K8sDeployment.yaml

Документация: «Раздел 7.2. Масштабирование».

АЗТ‑6 (P2 + F10 + S5)

Требование: Обработка заявки ≤ 10 сек (P2).

Решение: Асинхронный workflow с использованием Celery.

Обоснование:

Обработка заявок кол‑центром (F10).

Автотесты CI/CD (S5).

Трассировка:

Код: CeleryTask.ProcessDepositApplication()

Документация: «Раздел 8.1. Асинхронные процессы».

4. Ограничения архитектуры
АЗТ‑7 (+R2 + S2)

Требование: Совместимость с ASP.NET MVC 4.5 (+R2).

Решение: Использование Legacy Adapter для интеграции новых сервисов.

Обоснование: Снижение затрат на поддержку (S2).

Трассировка:

Код: LegacyAdapter.Mvc45Bridge

Документация: «Раздел 9.1. Поддержка legacy‑систем».

АЗТ‑8 (+R3 + F2)

Требование: Проверка личности в отделении (+R3).

Решение: Статус «Требуется визит» в заявке до подтверждения KYC.

Обоснование: Форма заявки содержит ФИО/телефон (F2).

Трассировка:

Код: ApplicationStatus.NeedsInPersonVerification

Документация: «Раздел 10.2. KYC‑процессы».

## Обоснование дополнительных требований

**1. Ограничение нагрузки на систему скоринга (+R4)**

**Почему:** Система скоринга критически важна для банка и испытывает пиковые нагрузки. Массовые предрасчёты могут привести к отказу сервиса.

**Решение:** Скоринг запускается только при явном запросе клиента (подача заявки).

**2. Запрет прямой интеграции с АБС (+R1)**

**Почему:** БД АБС уже перегружена. Прямой доступ из интернет‑банка увеличит нагрузку и риск сбоев.

**Решение:** Внедрение промежуточного сервиса-агрегатора данных.

**3. Горизонтальное масштабирование интернет‑банка (P3)**

**Почему:** Текущая инфраструктура (1 группа серверов) не выдерживает рост пользователей.

**Решение:** Развёртывание контейнеров в Kubernetes с автомасштабированием.

**4. Мониторинг и логирование (S4)**

**Почему:** Без отслеживания производительности невозможно выявлять узкие места.

**Решение:** Внедрение Prometheus + Grafana для визуализации метрик.

**5. Соблюдение требований ЦБ РФ (+R5)**

**Почему:** Банк обязан защищать персональные данные согласно ФЗ-152 и нормативам ЦБ.

**Решение:** Шифрование на уровне БД (TDE для Oracle/MS SQL), контроль доступа через RBAC.
